# 유사 밴픽 검색기 기획서

Nov 19, 2026 · @구예찬 · 개정 2 (실제 CSV 확인, 방향 논의 반영)

## 개요

리그 구분 없이 "같은 픽", "같은 맞대결", "비슷한 조합"이 나온 2026 시즌 대회 경기를 찾아 주는 개인용 분석 도구를 만든다.

- **왜**: 밴픽을 분석할 때 "이 조합이 다른 경기에서는 어떻게 흘러갔나"를 비교해야 하는데, 지금은 비슷한 경기를 손으로 찾아야 한다.
- **누구를 위해**: 나 (칼럼을 쓰는 분석가). 그리고 공개를 염두에 두고, 중계를 보는 팬과 칼럼 독자를 대상으로 한다 (아래 "방향").
- **더 큰 목표**: 데이터 수집·정제·검색·화면까지 직접 만든 경험을 GitHub에 남겨, 전력분석 포트폴리오이자 데이터 역량 포트폴리오로 쓴다.

**성공 기준**

- 챔피언 이름 몇 개를 넣으면 10초 안에 해당 경기 목록이 표로 나온다.
- 분석 중인 경기를 넣으면 픽이 가장 비슷한 경기 10개가 유사도 순으로 나온다.
- 첫 칼럼을 쓸 때 실제로 이 도구로 비교 경기를 찾는다.

## 방향 (논의 결과)

- **개편 (2026-11-21): 칼럼 사이트 + 개인 작업실**. 기록 사이트로는 dpm.lol·gol.gg와 규모에서 경쟁할 수 없고, 와우 포인트 후보(피어리스 계산기는 drafter.lol·uDrafter 등에 이미 있음, CL·스토브리그는 수요가 애매함)도 확인하지 못했다. 처음 목적(분석 역량 입증)으로 돌아가, **공개하는 것은 칼럼과 분석 노트뿐**이고 밴픽 검색기와 통계 화면은 칼럼을 쓰기 위한 개인 작업실로 둔다. 공개 사이트의 근거 상자는 빌드할 때 미리 계산해 싣기 때문에 전체 경기 데이터를 재배포하지 않는다(Oracle's Elixir 재배포 문제가 크게 줄어든다. 이용 조건 확인과 출처 표기는 여전히 필요). 데이터는 원본 165개 열을 모두 보존한다. 프로팀에는 스카우팅 리포트 형식의 글과 작업실 시연을, 분석 기업에는 분석 노트(기각한 가설과 정정 기록 포함)와 저장소를 보여 준다. 팬용 대시보드 버전은 태그 `v0-fan-dashboard`.
- **대상과 시점 (2026-11-20 개정)**: **응원하는 팀이 있는 팬이 중심**이다. 이긴 경기는 "왜 이겼나"를 되새기러, 어이없게 진 경기는 "뭐가 문제였나"를 찾으러, 경기가 끝난 **뒤에** 온다. 칼럼 독자는 칼럼을 통해 들어오는 두 번째 독자이고, 리그 전체를 중립적으로 분석하는 독자는 소수(주로 칼럼 작성자)로 본다. 실시간 갱신은 하지 않는다(원본이 하루 한 번 갱신된다).
- **설계 원칙**: 데이터는 "왜"를 증명하지 못한다. "이 경기에서 눈에 띈 점"과 "비슷한 경기에서는 어땠나"를 보여 주고 "이래서 졌다"고 단정하지 않는다. 팀·밴픽 단위로 보여 주고, 개인을 겨냥한 순위·비난 지표·댓글·투표는 만들지 않는다(악성 소비를 설계 목표로 삼지 않는다).
- **다시 오는 이유(Why)**: op.gg 계열은 "다음 판을 이기려고"(행동), Oracle's Elixir·Leaguepedia는 "기록을 조회하려고"(참조)다. 이 서비스는 **"방금 본 밴픽이 어떤 의미인지 이해시켜 준다"**. 승률과 스탯은 근거일 뿐 중심이 아니다.
- **기록 화면 (2026-11-20 추가)**: 분석 역량을 보여 주려면 기록이 바닥에 있어야 한다는 판단으로, 다른 사이트에서 좋았던 화면을 응원팀 기준으로 가져왔다. gol.gg의 팀 지표(경제·교전·오브젝트·시야, 진영별 승패, 용 종류, 진영별 밴)와 선수 표(KDA, 킬 관여, 피해·골드 비중, 챔피언), op.gg e스포츠의 챔피언 순위(리그·패치·포지션별 픽·밴, 티어는 뺌). 차이는 두 가지다. 팀 지표마다 **같은 리그 안 순위와 평균**을 붙여 숫자의 뜻을 읽게 했고, 챔피언을 누르면 그 챔피언이 나온 경기를 바로 찾는다. 순위는 팀 단위에만 붙이고 선수 표에는 붙이지 않는다(위 설계 원칙). Liquipedia처럼 팀 옆에 그림이 있는 목록은 로고 대신 엠블럼으로 한다(로고는 팀별 허락 필요). 한국어 기록은 인벤 기록실, Sheep Esports 한국어판이 있으나 응원팀 기준으로 묶어 읽어 주는 곳은 찾지 못했다. dpm.lol은 자동 접속이 막혀 아직 참고하지 못했다.
- **칼럼과의 관계**: 방문 이유는 칼럼이 만들고, 도구는 칼럼의 주장을 누구나 직접 확인하게 하는 근거가 된다.
- **와우 포인트 후보**: ② 밴픽 쌍둥이(같은 조합이 나온 경기를 짝으로), ③ 피어리스 시리즈 복기(세트별로 소진된 챔피언), ④ 스포일러 방지 모드(결과를 가리고 밴픽만 먼저). **폐기: ① 시즌 밴픽 지도.** 실제 2026 데이터의 팀 조합 19,880개로 시험한 결과, 무리가 서포터 챔피언 하나로 갈리고(같은 무리 안 유사도가 무작위의 3.7~4.7배), 패치·리그와는 거의 무관하며(월 NMI 0.03~0.05, 리그 0.01~0.02), 포지션까지 구분해도 같았다. 대신 챔피언 계열 구성(탱커·마법사·암살자)은 시즌 흐름에서 뚜렷하게 변한다(팀당 탱커 1.71 → 1.30 → 1.55 → 1.30, 암살자 0.74 → 1.21). **"메타 흐름" 차트가 대안 후보**다.
- **쌍둥이의 정의**: 양 팀 10명 중 8명 이상 같은 경기는 1.6%(157경기), 9명 이상은 0.2%뿐이다. 반면 한 팀 5명이 통째로 같은 다른 경기가 있는 경기는 17.7%다. 그래서 기본은 **팀 조합(5명) 쌍둥이**, 10명 중 7명 이상은 "드문 경기" 알림으로만 쓴다.
- **인기 픽**: 4세트 이상 시리즈에서 뽑히는 챔피언의 포지션 안 평균 인기 순위가 1세트 7.1위에서 5세트 13.8위로 내려가고, 5세트 시작 때 포지션별 인기 상위 8명(40명) 중 평균 24명이 이미 소진돼 있다. 그래서 "남은 챔피언 목록"이 아니라 "인기 상위 40명 중 몇 명이 소진됐나"를 보여 준다.
- **화면**: 서버 없는 정적 사이트(HTML/JS) + Python 전처리로 정했다 ([`docs/기술스택.md`](기술스택.md)). 기존 Streamlit 앱은 공개하지 않고 로컬 분석용으로만 남긴다.
- **칼럼**: `columns/*.md`에 글을 쓰고 `@search`, `@series`, `@game` 근거 상자를 끼우면 사이트가 데이터에서 직접 계산해 보여 준다 ([`docs/칼럼-작성법.md`](칼럼-작성법.md)).

## 기능 범위

첫 버전은 픽 기준 검색과 필터, 결과 표만 만든다. 밴은 유사도에 넣지 않는다 (이유는 "유사도 계산 방법" 참고).

| 단계 | 기능 | 예시 입력 | 결과 |
| --- | --- | --- | --- |
| MVP | 같은 챔피언 찾기 | 오리아나 + 바이 | 두 챔피언이 같은 팀에 있었던 경기 |
| MVP | 같은 맞대결 찾기 | 미드 아지르 vs 오리아나 | 같은 라인에서 맞붙은 경기 (양쪽 진영 모두) |
| MVP | 비슷한 조합 찾기 (양쪽) | 경기 하나의 픽 10개 | 두 팀 조합이 모두 비슷한 경기 10개 |
| MVP | 비슷한 조합 찾기 (한쪽) | 한 팀의 픽 5개 | 상대 조합과 상관없이 이 조합과 비슷한 경기 10개 |

## 데이터

기본 데이터는 Oracle's Elixir의 시즌별 CSV다. 아래 열 구성은 일반적으로 알려진 형태이며, **실제 파일을 받아 확인한 뒤 확정한다.**

- 경기 하나가 여러 줄로 나뉘어 있다: 선수 10명의 줄 + 팀 2개의 줄
- 경기 정보: 경기 ID, 리그, 날짜, 패치, 세트 번호
- 선수 줄: 팀, 진영, 포지션, 선수명, 챔피언
- 팀 줄: 밴 5개, 승패, 경기 시간, 10분·15분 골드 차이, 첫 드래곤·전령 등 오브젝트 지표

**2026 파일 확인 결과 (2026-11-19 받은 파일, 79MB)**

- 165개 열, **경기당 정확히 12줄**(선수 10 + 팀 2), 고유 경기 **9,940개**, 날짜 2026-01-01 ~ 11-18, 리그 44개.
- 선수 줄은 `position`이 top/jng/mid/bot/sup, 팀 줄은 `team`이다. 팀 줄의 `participantid`는 100(블루)/200(레드).
- **패치는 반드시 글자로 읽는다.** 숫자로 읽으면 `16.10`이 `16.1`이 되어 `16.01`과 섞인다 (`15.24`, `16.01`~`16.22`).
- 선수 줄의 챔피언은 빈 값이 0이라 **픽 10개는 모든 경기에서 완전**하다. 빈 값은 밴(315개 팀 줄), 골드차(174경기), 일부 경기의 팀 줄 픽 순서에 있고, 열 `datacompleteness`가 `partial`인 경기는 167개다.
- 팀 줄에 **`pick1`~`pick5`(픽 순서)**와 `ban1`~`ban5`가 있다. pick1~5는 선수 줄 챔피언과 99.2%가 같은 집합이다 → "밴픽 순서 반영"을 Leaguepedia 없이 할 수 있다.
- 팀 줄 `golddiffat15`는 각 팀 기준이고 블루와 레드가 정확히 반대 부호다(9,766경기 전부). `golddiffat10/20/25`, 첫 드래곤·전령·바론·타워, 경기 시간(초), 선수 이름도 있다.
- `year`는 2026(9,753경기), 2027(184경기), 2025(3경기)가 섞여 있다. 파일 이름 기준으로 모두 쓴다.
- 월즈(`WLDs`) 행은 `playoffs` 값이 0이고 `split`이 비어 있다. 월즈에서는 이 열을 믿을 수 없다.
- **시리즈 ID는 없다.** 게임 ID는 경기마다 독립이라, 같은 리그·같은 팀 쌍·세트 번호 연속·36시간 이내로 시리즈를 추정한다(4,523개 중 99.7%가 1세트부터 연속).
- **2026년 3세트 이상 시리즈 1,607개 전부에서 같은 챔피언이 반복되지 않았다 → 모든 리그가 피어리스.** 세트 번호 필터가 곧 피어리스 단계를 뜻한다.
- 챔피언 이름 173개 전부가 Data Dragon 영문 이름과 일치한다.

**전처리로 만들 표**: 경기 하나당 한 줄로 묶는다.

| 열 | 내용 |
| --- | --- |
| game_id, league, year, split, playoffs, datetime, date, patch(글자), set_no | 경기 정보 |
| blue_team, red_team, winner("blue"/"red") | 팀과 결과 |
| blue_top ~ blue_sup, red_top ~ red_sup | 포지션별 챔피언 10개 |
| blue_*_player, red_*_player | 포지션별 선수 이름 |
| blue_bans, red_bans, blue_pick_order, red_pick_order | 밴 목록, 픽 순서 |
| first_pick, first_dragon, first_herald, first_baron, first_tower | 첫 선택·오브젝트를 가져간 진영 |
| gd10, gd15, gd20, gd25, length_sec | 골드 차이(블루 기준), 경기 시간 |
| data_complete | 픽 10개가 모두 있고 원본이 complete인지 (아니면 "일부 누락" 표시) |
| series_id, series_games, series_ok | 추정한 시리즈 번호, 관측된 세트 수, 1세트부터 이어지는지 |

**데이터 제약**

- LPL 등 중국 리그는 라이엇이 직접 운영하지 않아 일부 항목이 비어 있을 수 있다. 빈 값은 검색에서 빼지 말고 "없음"으로 표시한다.
- 데이터 이용 조건은 Oracle's Elixir 사이트에서 확인하고, 도구를 공개할 때는 출처를 밝힌다.
- **원본 CSV와 전처리 결과(`games.parquet`)는 모두 GitHub에 올리지 않는다.** parquet도 원본에서 만든 파생 데이터라 재배포가 된다.

**대상 범위**: 2026 시즌 전 리그만 쓴다. 메타가 바뀐 과거 데이터는 비교에 잡음이 되기 때문이다. 필요하면 패치 범위 필터로 더 좁힌다.

**챔피언 이름**: 데이터는 영문 이름이지만 입력은 한글로 한다. 라이엇 공식 게임 데이터(Data Dragon)의 챔피언 id로 `ko_KR`과 `en_US`의 `name`을 이어 붙여 한글↔영문 대응표를 자동으로 만든다. Oracle's Elixir 표기("Nunu & Willump", "Wukong", "K'Sante" 등)는 영문 `name`과 대체로 일치한다. 전처리 때 대응표에 없는 이름이 나오면 경고로 출력해, 새 챔피언이나 표기 차이를 바로 알아챈다.

## 유사도 계산 방법

"비슷한 조합"은 두 경기에서 겹치는 **픽**이 얼마나 많은지로 계산하고, 밴은 넣지 않는다. 복잡한 모델 없이 설명 가능한 계산부터 시작한다.

**밴을 빼는 이유**

- 피어리스에서는 세트마다 밴의 뜻이 다르다. 1세트 밴은 메타 견제지만, 4~5세트 밴은 "남은 챔피언 중 위험한 것"을 고르는 일이 된다.
- 앞 세트에서 소진된 챔피언은 사실상 밴인데 밴 칸에는 나오지 않는다. 밴 칸만 비교하면 상황을 반만 본다.
- 이 도구의 목적은 "이 조합이 다른 경기에서 어떻게 흘러갔나"다. 경기 흐름을 만드는 것은 협곡에 있던 챔피언, 즉 픽이다.

밴의 영향은 유사도 대신 **세트 번호 필터**로 다룬다. 단, 세트 번호가 곧 피어리스 후반을 뜻하는 것은 피어리스 방식을 쓰는 대회에서뿐이다. 대회마다 방식이 다르므로 리그·대회 필터와 함께 쓴다. 밴 전략 자체를 보고 싶을 때는 다음 단계의 "밴 패턴 비슷한 경기 찾기"를 따로 만든다.

**계산 순서**

1. **필터 먼저**: 패치 범위, 리그, 세트 번호로 후보 경기를 거른다.
2. **팀 조합 점수 (자카드 유사도)**: 두 팀 조합(픽 5개씩)에서 "겹치는 챔피언 수 ÷ 합친 챔피언 수". 0이면 하나도 안 겹치고, 1이면 완전히 같다.
3. **한쪽 비교**: 한 팀 조합만 넣으면, 후보 경기의 두 팀 중 더 비슷한 쪽의 점수를 쓴다. 어느 쪽이 매칭됐는지를 결과 열에 남긴다. 이 정보가 없으면 승패를 해석할 수 없다.
4. **양쪽 비교**: 두 팀 조합을 다 넣으면, 각 팀의 점수를 평균 낸다. 진영이 바뀐 경우도 있으므로 "A-B"와 "B-A" 두 가지 짝을 모두 계산하고 더 높은 점수를 쓴다.
5. **포지션 보너스**: 넣지 않는다 ("결정 사항" 참고).
6. **정렬**: 점수 내림차순. 동점이면 최근 날짜 순.
7. **픽이 일부 없는 팀**: 있는 챔피언만으로 집합을 만들어 계산하되, 결과 표에 "일부 누락"을 표시한다. 경기를 결과에서 빼지는 않는다.

```latex
sim(T_1, T_2) = \frac{|T_1 \cap T_2|}{|T_1 \cup T_2|}
```

T는 한 팀의 픽 5개다. 예를 들어 두 조합이 3개를 공유하면 3 ÷ 7 ≈ 0.43이다. 먼저 이 계산으로 결과를 보고, "이 경기는 왜 비슷하다고 나왔지?"를 직접 확인하면서 포지션 보너스 같은 규칙을 더할지 정한다.

데이터가 한 시즌 1만 경기 안팎이라 후보 전체를 하나씩 비교해도 충분히 빠르다. 챔피언을 집합으로 저장해 두는 정도면 되고 별도 인덱스는 필요 없다.

## 시스템 구조와 기술 스택

서버나 DB 없이 내 PC에서 돌아가는 구조로 시작한다.

1. **원본 데이터**: Oracle's Elixir CSV를 `data/raw/`에 둔다.
2. **전처리**: 스크립트가 경기 하나당 한 줄짜리 표를 만들어 `data/games.parquet`로 저장한다. CSV를 바꾼 때만 다시 돌린다.
3. **검색 모듈**: 같은 챔피언 / 같은 맞대결 / 유사 조합 검색 함수 3개와 필터, 한글 이름 변환. 화면과 분리해서 테스트할 수 있게 한다.
4. **화면**: Streamlit 페이지 하나. 검색 종류 선택 → 챔피언 입력 → 결과 표.

| 역할 | 도구 | 이유 |
| --- | --- | --- |
| 언어 | Python | 이미 코테에서 쓰고 있음 |
| 데이터 처리 | pandas (+ pyarrow) | CSV 읽기, 묶기, 필터, parquet 저장 |
| 화면 | Streamlit | 파이썬 코드만으로 검색 화면을 빠르게 만듦 |
| 테스트 | pytest | 검색 함수가 맞는 경기를 찾는지 확인 |
| 코드 관리 | Git + GitHub | 포트폴리오로 보여 줄 기록 |

**폴더 구조**

```
draft-finder/
  data/              # 전체를 .gitignore에 넣음 (raw CSV, games.parquet 모두 비공개)
    raw/
  src/prepare.py     # 전처리
  src/search.py      # 검색 함수 3개 + 필터
  src/names.py       # 한글↔영문 챔피언 이름 대응
  app.py             # Streamlit 화면
  tests/             # 검색 테스트
    fixtures/        # 직접 만든 가짜 경기 몇 줄 (실제 데이터 없이 테스트하기 위함)
  docs/기획서.md
  requirements.txt
  README.md          # 무엇을, 왜, 어떻게 (데이터 받는 법 → prepare.py 실행 순서 포함)
```

## 개발 단계와 완료 기준

짬짬이 할 수 있게 한 단계를 1~2시간 단위로 자른다. 단계가 끝날 때마다 GitHub에 커밋한다.

- [x] **1. 데이터 확인**: CSV를 받아 열 이름과 한 경기가 몇 줄인지 확인하고, 이 기획서의 "데이터" 섹션을 실제에 맞게 고친다. 완료 기준: 월즈 결승 1세트의 10명 챔피언과 밴을 CSV에서 찾아 실제 경기와 맞는지 확인했다 (파일에 아직 없으면 다른 큰 경기로 대체).
- [x] **2. 전처리**: 경기 하나당 한 줄짜리 표 만들기. 완료 기준: 경기 수가 원본의 고유 경기 ID 수와 같다. (9,940 = 9,940 확인, `src/prepare.py`)
- [ ] **3. 같은 챔피언 찾기** 완료 기준: 월즈 결승에서 쓰인 조합을 넣으면 그 결승 세트가 결과에 나온다.
- [ ] **4. 같은 맞대결 찾기** 완료 기준: 포지션과 챔피언 두 개를 넣으면 양쪽 진영 모두의 경기가 나온다.
- [ ] **5. 유사 조합 찾기 (한쪽·양쪽) + 필터** 완료 기준: 경기 ID를 넣으면 유사도 1.0인 결과에 자기 자신이 포함되고(같은 픽의 다른 경기가 있으면 동점일 수 있음), 나머지 상위 결과가 눈으로 봐도 비슷하다.
- [ ] **6. 테스트 코드**: 3~5번의 완료 기준을 pytest로 자동 확인. 실제 데이터가 아니라 `tests/fixtures/`의 가짜 경기로 돌아가게 해서, 데이터가 없는 환경에서도 통과해야 한다.
- [ ] **7. Streamlit 화면** 완료 기준: 브라우저에서 검색 세 가지가 모두 동작한다.
- [ ] **8. README 작성**: 무엇을 왜 만들었고, 유사도를 어떻게 계산하고, 한계는 무엇인지. 화면 캡처 포함.

1~5단계는 화면 없이 코드만으로 할 수 있어서, 영상을 볼 수 없는 시간에 진행하기 좋다.
